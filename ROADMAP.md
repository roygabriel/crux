Based on what's already built (Phases 1A–14F) and what's planned (10A–12B), plus where the multi-agent orchestration space is heading in 2026, here are features I think would genuinely move the needle — organized by quarter with the highest-impact items first.
Q2 2026 — Reliability & Trust
Git Worktree Isolation — Right now agents share the working directory. The industry has converged on git worktrees as the solution: each agent gets its own worktree on its own branch, merges happen through the orchestrator. This eliminates file conflicts entirely instead of detecting them after the fact. Cursor tried shared-directory with locking and it slowed 20 agents to the throughput of 2-3. Worktrees are the fix.
Cost & Token Telemetry — Track token consumption per agent, per phase, per prompt. Expose it in the TUI and via crux stats. Users have no visibility into how much a session costs right now. This is table stakes for anyone running multi-agent sessions that burn through API credits. Include cumulative cost estimates using each provider's pricing.
Session Replay — Record every orchestrator decision, agent message, gate result, and phase transition as an event-sourced log. crux replay <session-id> plays it back in the TUI showing exactly what happened. This is critical for debugging "why did the orchestrator assign that task to the wrong agent at 2am" without having to grep through tmux scrollback.
Checkpoint & Resume — Serialize full session state (world state, agent progress, memory bank snapshot, phase position) to disk. crux resume picks up where you left off after a crash, reboot, or intentional pause. Without this, a 6-hour multi-agent session is lost if your laptop sleeps.
Q3 2026 — Scale & Automation
GitHub Issue → Phase Auto-Decomposition — Connect Crux to your issue tracker. When an issue is labeled crux-ready, the planning agent (14E) auto-decomposes it into phases and prompt docs, creates a PR with the phase files, and waits for human approval before executing. This is the "assign an issue to your AI team" workflow that GitHub Copilot and Jules are pushing — but self-hosted and CLI-native.
Webhook / Event-Driven Triggers — crux watch mode that triggers sessions on GitHub webhook events (push to branch, PR comment, issue creation). Combined with the above, this turns Crux into a CI-adjacent service that can respond to repo events without a human at the keyboard. Natural stepping stone toward running Crux on a server.
Parallel Phase Execution with Dependency Graph — The phase engine already tracks dependencies, but execution is sequential. Add a parallel scheduler that identifies phases with no unmet dependencies and runs them simultaneously across multiple agents. The Mermaid diagrams in the README already show the dependency graph — make the orchestrator actually exploit it.
Agent Performance Profiling — Track per-agent metrics: gate pass rate, average prompts-to-completion, error frequency, rate limit hits, token efficiency (tokens consumed per passing gate). Surface this in the TUI and use it for smarter assignment — the orchestrator should learn which agent/CLI performs best for which task category.
Q4 2026 — Intelligence & Ecosystem
Codebase Context Engine — Before assigning a task, automatically build a relevance-ranked context of the codebase: dependency graph, call graph, recent git blame, file ownership. Inject the most relevant files into the agent's prompt. This is what Anthropic's report calls "context engineering" and it's the biggest lever for agent output quality. Right now agents get what's listed in Required Reading — a static list. This makes it dynamic.
Multi-Repo / Monorepo Support — Orchestrate across multiple repositories or monorepo packages. Assign different agents to different packages with separate worktrees and merge strategies. Enterprise teams don't have single-repo projects.
Plugin Marketplace / Community Roles — Let users define custom roles beyond the five built-in ones and share them. A crux role install security-auditor that pulls a community-maintained role definition with specialized constraints, review checklists, and tool requirements. Same for custom preference presets (crux prefs install golang-strict-google-style).
Remote Execution Mode — Run Crux on a headless server (VPS, EC2) with the Telegram integration (11A) as the primary interface. SSH in to attach to the tmux session when needed, but monitor and approve remotely. This is the "agents work overnight" use case from Anthropic's trends report.
Ongoing / Cross-Cutting
Language Expansion — The preference system and role definitions are heavily Go-centric right now. Add TypeScript, Python, and Rust preset packs with language-appropriate testing frameworks, linter configs, error handling patterns, and conventions. Each language pack is a preference preset + role instruction addendum.
OpenTelemetry Integration — Emit spans for every orchestrator decision, agent message, gate execution, and phase transition. Export to Jaeger, Grafana, or any OTLP collector. This gives teams with existing observability stacks immediate visibility into Crux sessions without learning a new tool.
Crux MCP Server — Expose Crux itself as an MCP server so other tools (Claude Code, Cursor, VS Code Copilot) can invoke crux start, crux status, crux plan as tools. This inverts the relationship: instead of Crux orchestrating agents, agents can orchestrate Crux. Useful for meta-orchestration workflows where a senior Claude Code session manages multiple Crux projects.

If I had to pick the three that would differentiate Crux most from the competitors I found in the audit (NTM, Agent Deck, Uzi, Codex-Orchestrator), it would be git worktree isolation (most competitors don't do this properly), issue → phase auto-decomposition (nobody has this), and checkpoint & resume (every competitor loses state on crash). The phase system is already your unique moat — extending it with auto-decomposition from issues makes it a complete workflow, not just a task runner.
